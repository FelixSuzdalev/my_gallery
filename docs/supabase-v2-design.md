# Supabase V2 Design

Дата: 2026-06-23  
Ветка: `feature/supabase-v2`  
Источник: `docs/supabase-v1-audit.md`

Документ описывает проект новой схемы Supabase V2 для виртуальной галереи. Это не SQL-миграция и не инструкция к немедленному изменению Supabase. Цель V2: сохранить текущий V1-контракт приложения, добавить нормальное хранение медиа, разделить лайки и избранное, подготовить комментарии и подписки.

## Принципы V2

- Существующие таблицы остаются совместимыми: `profiles`, `artworks`, `favorites`, `events`, `collections`, `collection_items`.
- Поля, на которые опирается текущий код, не удаляются и не переименовываются.
- `profiles.id` остается равным `auth.users.id`.
- Роли остаются строками `user`, `creator`, `admin`.
- `artworks.tags` в первой версии V2 остается `text[]`.
- На этом этапе не вводятся отдельные таблицы `tags` и `artwork_tags`.
- Новые возможности добавляются рядом с V1, а не вместо V1.

## Совместимые V1 Таблицы

### `profiles`

Сохранить поля:

- `id`
- `username`
- `full_name`
- `avatar_url`
- `bio`
- `role`

Контракт:

- `id` совпадает с `auth.users.id`.
- `role` принимает значения `user`, `creator`, `admin`.
- `username` должен оставаться пригодным для открытия `/profile/[id]`, где `[id]` может быть UUID или username.
- `avatar_url` в V2 пока остается готовым URL для совместимости с текущими `<img src={...}>`.

Возможные V2-добавления без ломки кода:

- `created_at`
- `updated_at`
- `deleted_at` для мягкого удаления вместо client-side hard delete.
- `is_public`

### `artworks`

Сохранить поля:

- `id`
- `title`
- `description`
- `image_url`
- `author_id`
- `tags`
- `created_at`

Контракт:

- `author_id` продолжает ссылаться на `profiles.id`.
- `tags` остается `text[]`, потому что текущий код использует `.contains('tags', ...)` и `.overlaps('tags', ...)`.
- `image_url` пока остается главным совместимым preview URL.

Возможные V2-добавления без ломки кода:

- `updated_at`
- `status` для draft/published/archived.
- `visibility` для public/unlisted/private.
- Главная картинка работы в первой версии V2 определяется как запись `artwork_media` с `sort_order = 0`.
- `primary_media_id` не включать в ближайшую первую миграцию; его можно добавить позднее отдельной миграцией.

### `favorites`

Сохранить поля:

- `id`
- `user_id`
- `artwork_id`

Контракт:

- В V1 таблица одновременно работает как лайки и избранное.
- В V2 таблицу лучше закрепить за избранным/сохраненными работами.
- Для совместимости текущий код может временно продолжать считать `favorites` лайками.

Ограничения:

- Один пользователь не должен иметь два одинаковых избранных для одной работы.
- Пара `user_id + artwork_id` должна быть уникальной.

### `events`

Сохранить текущий контракт:

- `id`
- `title`
- `description`
- `location_name`
- `start_date`
- `end_date`
- `external_url`
- `created_at`

Возможные V2-добавления:

- `status`
- `cover_media_id`
- `updated_at`

### `collections`

Сохранить поля:

- `id`
- `title`
- `description`
- `created_at`

Возможные V2-добавления:

- `created_by`
- `updated_at`
- `visibility`
- `sort_order`

### `collection_items`

Сохранить поля:

- `id`
- `collection_id`
- `artwork_id`
- `position`

Контракт:

- Связь `artwork:artworks(*)` должна остаться доступной для текущего кода.
- `position` продолжает задавать порядок работ в подборке.

## Новые Таблицы V2

### `artwork_media`

Назначение: отдельное хранение медиафайлов работ вместо зависимости только от `artworks.image_url`.

Поля:

- `id`
- `artwork_id`
- `bucket_id`
- `storage_path`
- `media_type`
- `alt_text`
- `width`
- `height`
- `sort_order`
- `created_at`

Рекомендации:

- `artwork_id` ссылается на `artworks.id`.
- `bucket_id` хранит bucket: обычно `artwork-media` или `artwork-originals`.
- `storage_path` хранит путь внутри bucket, а не полный public URL.
- `media_type` на первом этапе: `image`, позже можно расширить до `video`, `model`, `document`.
- `sort_order` задает порядок медиа внутри работы.
- Для совместимости `artworks.image_url` остается preview URL и может заполняться из первого public media.

### `artwork_likes`

Назначение: отдельные лайки работ, чтобы отделить их от избранного.

Поля:

- `id`
- `user_id`
- `artwork_id`
- `created_at`

Ограничения:

- Один пользователь может поставить только один лайк одной работе.
- Пара `user_id + artwork_id` должна быть уникальной.
- `user_id` ссылается на `profiles.id`.
- `artwork_id` ссылается на `artworks.id`.

Поведение:

- `favorites` остается для сохраненных работ.
- `artwork_likes` становится источником счетчика лайков после обновления интерфейса.

### `comments`

Назначение: комментарии к работам и ответы на комментарии.

Поля:

- `id`
- `artwork_id`
- `author_id`
- `parent_id`
- `body`
- `status`
- `created_at`
- `updated_at`

Рекомендации:

- `artwork_id` ссылается на `artworks.id`.
- `author_id` ссылается на `profiles.id`.
- `parent_id` ссылается на `comments.id` и нужен для ответов.
- `parent_id` может ссылаться только на комментарий с тем же `artwork_id`.
- Это правило нужно проверять на уровне БД или безопасной серверной операции.
- `status` на первом этапе: `visible`, `hidden`, `deleted`, `pending`.
- Удаление пользовательского комментария лучше делать через `status = deleted`, а не физическим удалением.

### `follows`

Назначение: подписки между пользователями.

Поля:

- `follower_id`
- `following_id`
- `created_at`

Ограничения:

- `follower_id` ссылается на `profiles.id`.
- `following_id` ссылается на `profiles.id`.
- Пользователь не может подписаться сам на себя.
- Пара `follower_id + following_id` должна быть уникальной.
- Отдельный `id` не обязателен: естественный ключ пары подходит для первой версии.

## Агрегированная статистика работ

Для перехода V1 -> V2 нужен compatibility-safe слой `artwork_stats` в виде view или RPC. Он должен возвращать агрегированные числа без раскрытия персональных строк `favorites`, `artwork_likes` и `comments`.

Поля:

- `artwork_id`
- `likes_count`
- `favorites_count`
- `comments_count`

Контракт:

- `likes_count` считается из `artwork_likes`.
- `favorites_count` считается из `favorites`.
- `comments_count` считается из `comments`; для публичных экранов учитываются только видимые комментарии.
- Текущая лента V1 считает `favorites` как популярность, поэтому нельзя сразу ограничить чтение `favorites` только владельцем без отдельного агрегированного слоя.
- После появления `artwork_stats` можно ужесточать RLS для сырых таблиц `favorites` и `artwork_likes`, оставляя публичными только агрегаты.

## Storage Buckets

Важно: public bucket означает, что любой, кто знает URL объекта, может открыть файл. Поэтому `avatars` и `artwork-media` допустимо оставить public, а `artwork-originals` должен быть private.

### `avatars`

Назначение: аватары пользователей.

- Доступ: public.
- Читать: все пользователи и гости.
- Загружать: владелец профиля для себя, admin для любого пользователя.
- Удалять: владелец профиля для себя, admin для любого пользователя.
- Формат новых путей: `{user_id}/avatar-{uuid}.{ext}`.
- Совместимость: существующие public URL из V1 должны продолжать открываться; `profiles.avatar_url` пока хранит готовый URL.

### `artwork-media`

Назначение: оптимизированные публичные изображения работ для отображения в галерее.

- Доступ: public.
- Читать: все пользователи и гости.
- Загружать: author/creator своей работы, admin любой работы.
- Удалять: author/creator своей работы, admin любой работы.
- Формат путей: `{author_id}/{artwork_id}/display/{sort_order}-{uuid}.{ext}`.
- `author_id` в пути упрощает безопасные Storage RLS-политики: по первому сегменту пути можно быстро сверить владельца и автора работы.
- Связь с БД: каждая загрузка фиксируется в `artwork_media` с `bucket_id = artwork-media`.

### `artwork-originals`

Назначение: исходники работ в максимальном качестве.

- Доступ: private.
- Читать: author/creator своей работы, admin; публичный UI не читает напрямую.
- Загружать: author/creator своей работы, admin.
- Удалять: author/creator своей работы, admin.
- Формат путей: `{author_id}/{artwork_id}/original/{uuid}.{ext}`.
- `author_id` в пути упрощает безопасные Storage RLS-политики для private исходников.
- Связь с БД: запись в `artwork_media` может хранить `bucket_id = artwork-originals`, но public preview должен идти через `artwork-media` или `artworks.image_url`.

### `event-media`

Назначение: обложки и медиа событий.

- Доступ: public для опубликованных событий.
- Выбор public/private для `event-media` зависит от того, будут ли у событий черновики. Если медиа черновиков не должны открываться по URL, bucket должен быть private или нужен отдельный private bucket для draft-media.
- Читать: все пользователи и гости.
- Загружать: admin.
- Удалять: admin.
- Формат путей: `{event_id}/cover/{uuid}.{ext}` или `{event_id}/gallery/{sort_order}-{uuid}.{ext}`.
- Связь с БД: в V2 можно добавить `events.cover_media_id`, но текущий код продолжит использовать fallback-картинку до обновления интерфейса.

## RLS Правила Простым Языком

### `profiles`

- Гости и пользователи могут читать публичные поля профилей.
- Пользователь может обновлять свой `full_name`, `username`, `avatar_url`, `bio`.
- Обычный пользователь не может менять `role`.
- Обычный пользователь не может физически удалить профиль.
- Только admin может менять `role`.
- Изменение `role`, блокировка и мягкое удаление профиля должны постепенно переноситься в защищенный серверный слой.
- Для soft delete использовать `deleted_at`.
- Client-side удаление профиля должно быть запрещено или заменено на мягкое удаление через серверную/admin-операцию.
- Связь `profiles.id = auth.users.id` обязательна.

### `artworks`

- Гости и пользователи могут читать опубликованные публичные работы.
- Creator может создавать работы от своего `author_id`.
- Creator может редактировать свои работы.
- Admin может создавать, редактировать и удалять любые работы.
- Физическое удаление лучше ограничить admin-ролью; для creator предпочтительно `status = archived`.
- `tags` остаются доступными для фильтрации.

### `favorites`

- Пользователь может читать свои favorites.
- Пользователь может добавлять работу в свои favorites.
- Пользователь может удалять только свои favorites.
- Admin может читать все favorites для модерации и аналитики.
- Дубликаты `user_id + artwork_id` запрещены.

### `artwork_likes`

- Все могут читать количество лайков опубликованных работ.
- Пользователь может видеть свои лайки.
- Пользователь может поставить лайк только от своего `user_id`.
- Пользователь может удалить только свой лайк.
- Дубликаты `user_id + artwork_id` запрещены.
- Admin может читать все лайки, но обычно не должен менять пользовательские лайки без модерационной причины.

### `comments`

- Гости и пользователи могут читать комментарии со статусом `visible` у опубликованных работ.
- Авторизованный пользователь может создать комментарий от своего `author_id`.
- Автор комментария может редактировать свой комментарий, пока он не скрыт модерацией.
- Автор комментария может мягко удалить свой комментарий через `status = deleted`.
- Admin может скрывать, восстанавливать и модерировать любые комментарии.
- Ответы разрешены через `parent_id`, если родительский комментарий относится к той же работе.
- Правило совпадения `parent_id.artwork_id` и `comments.artwork_id` должно проверяться на уровне БД или безопасной серверной операции.

### `follows`

- Пользователь может читать свои подписки и подписчиков публичных профилей.
- Пользователь может создать подписку только от своего `follower_id`.
- Пользователь может удалить только свою подписку.
- Подписка на самого себя запрещена.
- Дубликаты `follower_id + following_id` запрещены.
- Admin может читать все follows для модерации.

### `artwork_media`

- Все могут читать public media для опубликованных работ из `artwork-media`.
- Private originals из `artwork-originals` читают только author/creator своей работы и admin.
- Creator может добавлять media только к своей работе.
- Creator может редактировать metadata media своей работы: `alt_text`, `sort_order`.
- Admin может управлять media любых работ.
- Удаление media должно проверять и запись БД, и объект Storage.

### `collections`

- Все могут читать публичные коллекции.
- Только admin может создавать и редактировать коллекции в текущей модели.
- Если позже появятся пользовательские коллекции, понадобится `created_by` и отдельные политики для владельца.
- Физическое удаление коллекций лучше оставить только admin.

### `collection_items`

- Все могут читать элементы публичных коллекций.
- Только admin может добавлять, удалять и менять порядок элементов текущих командных подборок.
- Связь с `artworks` должна оставаться совместимой с `artwork:artworks(*)`.

#### Storage Buckets

- `avatars`: public read; upload/delete только владелец или admin.
- `artwork-media`: public read; upload/delete creator своей работы или admin.
- `artwork-originals`: private read; доступ только creator своей работы или admin.
- `event-media`: public или private в зависимости от наличия черновиков событий; upload/delete только admin.
- Любая операция upload/delete должна проверять не только auth user, но и право пользователя на связанный `profile`, `artwork` или `event`.

## Опасные Места V1

- Client-side удаление `profiles`.
  - Сейчас админские страницы вызывают `profiles.delete().eq('id', id)` из клиента. В V2 это нужно ограничить RLS и постепенно заменить на серверную или мягкую операцию.
- Client-side изменение `role`.
  - `components/admin/AuthorForm.tsx` и `app/admin/authors/page.tsx` меняют `profiles.role` из клиента. В V2 роль должен менять только admin, а RLS должна запрещать self-escalation.
- Использование `SUPABASE_SERVICE_ROLE_KEY`.
  - `app/api/auth/check-confirmation/route.ts` использует service role и fallback `auth.admin.listUsers`. Это допустимо только на сервере, но требует строгого контроля env и минимизации поверхности API.
- `favorites` смешивает лайки и избранное.
  - Текущий UI считает favorites как лайки и как сохраненные работы. V2 разделяет `favorites` и `artwork_likes`.
- `image_url` как готовый URL.
  - Текущий код ожидает готовую ссылку. V2 вводит `artwork_media`, но оставляет `artworks.image_url` для совместимости.
- `select('*')`.
  - В V1 есть `select('*')` для `artworks`, `collections`, `collection_items`. Это делает схему хрупкой и может тянуть лишние поля.
- Отсутствие отдельного хранения медиафайлов.
  - Сейчас работы опираются на строковый `image_url`, а Storage напрямую используется только для `avatars`. V2 добавляет `artwork_media` и Storage buckets для работ и событий.

## Порядок Внедрения V2

### Фаза 1 — база и RLS

- Зафиксировать V1-контракт таблиц и обязательных полей.
- Добавить новые таблицы V2 концептуально рядом с V1: `artwork_media`, `artwork_likes`, `comments`, `follows`.
- Настроить ограничения уникальности для `favorites`, `artwork_likes`, `follows`.
- Настроить RLS так, чтобы текущий V1-код продолжил работать, но опасные операции были ограничены ролью admin.
- Проверить, что `profiles.id = auth.users.id` сохраняется.

### Фаза 1.5 — агрегированная статистика и compatibility layer

- Подготовить compatibility-safe слой `artwork_stats` как view или RPC.
- Возвращать `artwork_id`, `likes_count`, `favorites_count`, `comments_count`.
- Сохранить совместимость с V1-лентой, которая считает `favorites` как популярность.
- Не закрывать чтение `favorites` только владельцем до появления агрегированного слоя для публичных счетчиков.
- После проверки `artwork_stats` постепенно переводить интерфейс и RLS на агрегаты вместо чтения сырых строк.

### Фаза 2 — Storage


- Подготовить buckets `avatars`, `artwork-media`, `artwork-originals`, `event-media`.
- Описать и проверить политики чтения, загрузки и удаления.
- Сохранить совместимость существующих `profiles.avatar_url`.
- Не ломать текущий `artworks.image_url`.

### Фаза 3 — работы и загрузка изображений

- Начать записывать новые загрузки работ в `artwork_media`.
- Для public preview заполнять `artworks.image_url` из `artwork_media` с `sort_order = 0`.
- Для оригиналов использовать private bucket `artwork-originals`.
- После обновления интерфейса перейти от ручного URL к управляемой загрузке.

### Фаза 4 — лайки и избранное

- Оставить `favorites` как избранное.
- Перенести поведение лайков в `artwork_likes`.
- Обновить счетчики популярности, чтобы они читали `artwork_likes`.
- На переходном этапе можно синхронизировать старые `favorites` в `artwork_likes`, если нужно сохранить текущие лайки.

### Фаза 5 — комментарии

- Включить `comments` для опубликованных работ.
- Начать с простого статуса `visible`.
- Добавить модерацию через `hidden`, `deleted`, `pending`.
- Ответы включать через `parent_id`.

### Фаза 6 — подписки

- Включить `follows`.
- Запретить self-follow и дубликаты.
- Добавить счетчики подписчиков и подписок на уровне запросов или materialized view позже.

### Фаза 7 — обновление интерфейса

- Убрать зависимость новых экранов от `select('*')`.
- Разделить UI "лайк" и "избранное".
- Добавить загрузку media вместо ручного `image_url`.
- Добавить комментарии и подписки.
- Перевести админские операции ролей и удаления на более безопасный серверный слой.

### Фаза 8 — миграция данных и переключение production

- Сделать backup V1.
- Перенести существующие `image_url` в `artwork_media` как legacy public media, где возможно.
- Сохранить `artworks.image_url` для обратной совместимости.
- Решить, какие `favorites` считаются избранным, а какие нужно скопировать в `artwork_likes`.

## Принятые Решения

- V2 строится как расширение V1, а не замена V1.
- Старые таблицы и поля остаются совместимыми с текущим кодом.
- `artworks.tags` остается `text[]` в первой версии V2.
- `favorites` закрепляется за избранным, а лайки выносятся в `artwork_likes`.
- Медиа работ выносится в `artwork_media`, но `artworks.image_url` остается совместимым preview URL.
- Добавляется compatibility-safe слой `artwork_stats` для публичных счетчиков `likes_count`, `favorites_count`, `comments_count`.
- `avatars` остается public bucket, `artwork-media` public, `artwork-originals` private; `event-media` выбирается public или private в зависимости от черновиков событий.
- Роли остаются `user`, `creator`, `admin`; изменение роли должно быть жестко ограничено admin-доступом.
